psql -c "show client_encoding;"


读完了。import_all.sh 是 Ora2Pg 18.2 标准生成的，从它能看到几个关键事实，正好帮你把两个方案都定下来。

从脚本里能确认的三件事

1. 你的导入脚本里没有任何"转码"动作。 数据导入就是一句 psql -f data/data.sql（脚本里还有一条直连回退：ora2pg -t COPY --pg_dsn ... --pg_user ...）。所以编码对不对，完全取决于「文件的字节」和「psql 的 client_encoding」是否一致。

2. DB 是 EUC-JP 时，psql 默认 client_encoding = EUC_JP。 这意味着：
- 文件是 EUC-JP + 不设任何环境变量 → psql 原样写进去，零转换、零报错——这就是方案一最对症的原因；
- 你现在报 UTF-8 字符 no equivalent，说明你当前环境里 client_encoding 是 UTF8（多半 PGCLIENTENCODING=UTF8 或库连接参数设了 UTF8），PG 被迫做 UTF8→EUC_JP 转换，才把不可映射字符顶出来的。普通表内容恰好都能映射所以"成功"，分割表里有个把字映射不了就炸——两者用的是同一批 UTF-8 文件，这跟你观察到的一致。

3. 方案的可行性差异，脚本里写死了： 直连回退是 -t COPY，而 PostgreSQL 的 COPY FROM 目标不能是视图。分割表在 PG 里已经是 view + INSTEAD OF trigger，所以"ora2pg 直连导分割表"这条路物理上走不通——这正是你最早说"ora2pg 不能动态导入"的原因，方案二对分割表不成立，只能走"文件 → psql"。

所以正确的做法收敛成一条路

① 源头：ora2pg.conf 改编码并重导
OUTPUT_ENCODING   EUC-JP
导出的数据文件/分割表文件就直接是 EUC-JP。导出时 NLS_LANG 也要与 Oracle 库一致（export NLS_LANG=JAPANESE_JAPAN.JA16EUC），否则读 Oracle 那一侧先出问题。

② 导入：别再用 UTF8 客户端
unset PGCLIENTENCODING        # 或 export PGCLIENTENCODING=EUC_JP
psql -h <pg> -U <owner> -d <db> -f data/data.sql
文件是 EUC-JP、client_encoding 是 EUC-JP、库是 EUC-JP，三者一致 → 无转换，就不 all.sh 可以照用（-f 跳过建库动作、用 -e 那套不需要）。



#!/bin/bash

# ==========================================
# PostgreSQL 自动化部署与 DDL 导入脚本
# ==========================================

# 1. 配置参数（请根据实际需求修改）
DB_HOST="localhost"
DB_PORT="5432"
# 超级管理员账号（用于创建表空间、用户、数据库）
ADMIN_USER="postgres"
# 如果超级管理员有密码，可以在执行脚本时通过 PGPASSWORD 环境变量传入，或配置 ~/.pgpass

# 新环境配置
TABLESPACE_NAME="my_tablespace"
TABLESPACE_PATH="/data/postgres/tablespaces/my_ts" # 确保该目录对 postgres 用户可读写
DB_USER="my_app_user"
DB_PASSWORD="MySecurePassword123"
DB_NAME="my_app_db"
SCHEMA_NAME="my_schema"
DDL_FILE="schema.sql"

# 检查 DDL 文件是否存在
if [ ! -f "$DDL_FILE" ]; then
    echo "错误: 找不到 DDL 文件: $DDL_FILE"
    exit 1
fi

echo "=========================================="
echo "开始执行 PostgreSQL 初始化部署..."
echo "=========================================="

# 2. 创建表空间（注意：目录通常需要 PostgreSQL 系统用户有权限访问）
echo "[1/5] 创建表空间: ${TABLESPACE_NAME}..."
psql -h "$DB_HOST" -p "$DB_PORT" -U "$ADMIN_USER" -d postgres <<EOF
-- 如果表空间目录不存在，请确保操作系统层面已创建并授权
-- 示例: sudo mkdir -p /data/postgres/tablespaces/my_ts && sudo chown postgres:postgres /data/postgres/tablespaces/my_ts
CREATE TABLESPACE IF NOT EXISTS ${TABLESPACE_NAME} LOCATION '${TABLESPACE_PATH}';
EOF

# 3. 创建数据库用户
echo "[2/5] 创建数据库用户: ${DB_USER}..."
psql -h "$DB_HOST" -p "$DB_PORT" -U "$ADMIN_USER" -d postgres <<EOF
DO \$\$
BEGIN
   IF NOT EXISTS (SELECT FROM pg_catalog.pg_roles WHERE rolname = '${DB_USER}') THEN
      CREATE ROLE ${DB_USER} LOGIN PASSWORD '${DB_PASSWORD}';
   END IF
END
\$\$;
EOF

# 4. 创建数据库并指定所有者和表空间
echo "[3/5] 创建数据库: ${DB_NAME}..."
psql -h "$DB_HOST" -p "$DB_PORT" -U "$ADMIN_USER" -d postgres <<EOF
SELECT 'CREATE DATABASE ${DB_NAME} OWNER ${DB_USER} TABLESPACE ${TABLESPACE_NAME}'
WHERE NOT EXISTS (SELECT FROM pg_database WHERE datname = '${DB_NAME}')\gexec
EOF

# 5. 在新数据库中创建 Schema 并授权
echo "[4/5] 创建 Schema: ${SCHEMA_NAME} 并授权..."
psql -h "$DB_HOST" -p "$DB_PORT" -U "$ADMIN_USER" -d "${DB_NAME}" <<EOF
CREATE SCHEMA IF NOT EXISTS ${SCHEMA_NAME} AUTHORIZATION ${DB_USER};
GRANT ALL PRIVILEGES ON DATABASE ${DB_NAME} TO ${DB_USER};
GRANT ALL ON SCHEMA ${SCHEMA_NAME} TO ${DB_USER};
EOF

# 6. 导入预先写好的 DDL 文件
echo "[5/5] 正在导入 DDL 文件: ${DDL_FILE}..."
# 使用新用户、新数据库连接，并将 DDL 导入到指定数据库中
export PGPASSWORD="${DB_PASSWORD}"
psql -h "$DB_HOST" -p "$DB_PORT" -U "$DB_USER" -d "${DB_NAME}" -f "${DDL_FILE}"
unset PGPASSWORD

echo "=========================================="
echo "恭喜！数据库初始化及 DDL 导入全部完成！"
echo "=========================================="




针对 Oracle 迁移到 PostgreSQL 过程中遇到的“无主键表”和“表被拆分”这两大经典数据校验难题，传统的基于主键比对的工具（如 Ora2Pg 自带的校验）确实无能为力。

针对这两种特殊情况，推荐使用以下成熟的解决方案和变通策略：

一、 针对“无主键表”的校验方法
当表没有主键时，无法通过 PRIMARY KEY 匹配行。核心解决思路是“全行内容哈希化（Row-level Hash）”或“引入临时行号”。

方法 1：全字段 MD5/SHA256 哈希比对（最推荐）
将每一行的所有列拼接成一个字符串，计算其哈希值（MD5），然后比对两边哈希值的集合是否一致。

Oracle 端查询示例：

SQL
-- 将各列用分隔符拼接后取 MD5
SELECT MD5(TO_CLOB(NVL(col1, 'NULL') || '|' || NVL(TO_CHAR(col2), 'NULL') || '|' || ...)) as row_hash
FROM source_table;
PostgreSQL 端查询示例：

SQL
-- 使用 row_to_json 或 string_agg 将整行转为文本并取 md5
SELECT md5(row_to_json(t)::text) as row_hash
FROM target_table t;
比对方式：将两边导出的哈希值列表导入到文件或临时表中，使用 comm、diff 或 SQL 的 EXCEPT 找出差异。

方法 2：基于临时序号（Row Number）的比对
如果表的数据量不是极大，且在导出期间表数据是静态的（无并发写入）：

在 Oracle 和 PostgreSQL 中分别通过分析函数 ROW_NUMBER() OVER (ORDER BY (SELECT NULL)) 生成一个确定性的临时行号。

将行号作为“虚拟主键”，按批次拉取进行字段逐一比对。

二、 针对“迁移后被分割的表”的校验方法
如果 Oracle 的一张大表在 PG 中被拆分成了多张表（例如按时间分区、按业务维度拆分，或分库分表），校验时需要将 PG 侧的数据“在逻辑上还原”。

方法 1：在 PostgreSQL 中创建“还原视图”（推荐）
在 PostgreSQL 中建立一个视图（View），通过 UNION ALL 或 JOIN 把被分割的表重新拼回原 Oracle 表的结构。

操作步骤：

在 PG 中创建视图：

SQL
CREATE OR REPLACE VIEW v_merged_original_table AS
SELECT * FROM table_part_2025
UNION ALL
SELECT * FROM table_part_2026;
之后，将这个视图 v_merged_original_table 直接当作一张完整的表，与 Oracle 的原表进行行数、聚合指标或上述的哈希比对。

方法 2：聚合指标分组合并校验（适合超大表）
如果数据量太大无法整体拼接，可以对比分组统计指标：

Oracle 端：按某个公共维度（如日期、状态、业务类型）统计 COUNT(*) 和关键数值列的 SUM()。

PG 端：对所有拆分表的数据进行相同的聚合统计，并将结果汇总。

比对内容：核对各个分组的 COUNT 和 SUM 是否完全一致。

三、 生产环境常用校验工具推荐
如果不想手写复杂的 SQL 脚本，可以借助以下两款专门处理复杂异构数据库校验的开源/成熟工具：

DataChecker / DataX-Cert：支持异构数据库（Oracle vs PG）的抽样对比和全量/增量对账，支持自定义无主键表的联合键或全字段校验。

Python 自研校验脚本（Pandas）：

用 Python 分页读取 Oracle 和 PG 数据。

利用 pandas.merge() 或 pd.concat() 在内存中处理拆分表的合并，并使用 df.equals() 或多列差集快速找出不一致的数据行。
