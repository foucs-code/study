psql -c "show client_encoding;"


读完了。import_all.sh 是 Ora2Pg 18.2 标准生成的，从它能看到几个关键事实，正好帮你把两个方案都定下来。

从脚本里能确认的三件事

1. 你的导入脚本里没有任何"转码"动作。 数据导入就是一句 psql -f data/data.sql（脚本里还有一条直连回退：ora2pg -t COPY --pg_dsn ... --pg_user ...）。所以编码对不对，完全取决于「文件的字节」和「psql 的 client_encoding」是否一致。

2. DB 是 EUC-JP 时，psql 默认 client_encoding = EUC_JP。 这意味着：
- 文件是 EUC-JP + 不设任何环境变量 → psql 原样写进去，零转换、零报错——这就是方案一最对症的原因；
- 你现在报 UTF-8 字符 no equivalent，说明你当前环境里 client_encoding 是 UTF8（多半 PGCLIENTENCODING=UTF8 或库连接参数设了 UTF8），PG 被迫做 UTF8→EUC_JP 转换，才把不可映射字符顶出来的。普通表内容恰好都能映射所以"成功"，分割表里有个把字映射不了就炸——两者用的是同一批 UTF-8 文件，这跟你观察到的一致。

3. 方案的可行性差异，脚本里写死了： 直连回退是 -t COPY，而 PostgreSQL 的 COPY FROM 目标不能是视图。分割表在 PG 里已经是 view + INSTEAD OF trigger，所以"ora2pg 直连导分割表"这条路物理上走不通——这正是你最早说"ora2pg 不能动态导入"的原因，方案二对分割表不成立，只能走"文件 → psql"。

所以正确的做法收敛成一条路

① 源头：ora2pg.conf 改编码并重导
OUTPUT_ENCODING   EUC-JP
导出的数据文件/分割表文件就直接是 EUC-JP。导出时 NLS_LANG 也要与 Oracle 库一致（export NLS_LANG=JAPANESE_JAPAN.JA16EUC），否则读 Oracle 那一侧先出问题。

② 导入：别再用 UTF8 客户端
unset PGCLIENTENCODING        # 或 export PGCLIENTENCODING=EUC_JP
psql -h <pg> -U <owner> -d <db> -f data/data.sql
文件是 EUC-JP、client_encoding 是 EUC-JP、库是 EUC-JP，三者一致 → 无转换，就不 all.sh 可以照用（-f 跳过建库动作、用 -e 那套不需要）。



#!/bin/bash

# ==========================================
# PostgreSQL 自动化部署与 DDL 导入脚本
# ==========================================

# 1. 配置参数（请根据实际需求修改）
DB_HOST="localhost"
DB_PORT="5432"
# 超级管理员账号（用于创建表空间、用户、数据库）
ADMIN_USER="postgres"
# 如果超级管理员有密码，可以在执行脚本时通过 PGPASSWORD 环境变量传入，或配置 ~/.pgpass

# 新环境配置
TABLESPACE_NAME="my_tablespace"
TABLESPACE_PATH="/data/postgres/tablespaces/my_ts" # 确保该目录对 postgres 用户可读写
DB_USER="my_app_user"
DB_PASSWORD="MySecurePassword123"
DB_NAME="my_app_db"
SCHEMA_NAME="my_schema"
DDL_FILE="schema.sql"

# 检查 DDL 文件是否存在
if [ ! -f "$DDL_FILE" ]; then
    echo "错误: 找不到 DDL 文件: $DDL_FILE"
    exit 1
fi

echo "=========================================="
echo "开始执行 PostgreSQL 初始化部署..."
echo "=========================================="

# 2. 创建表空间（注意：目录通常需要 PostgreSQL 系统用户有权限访问）
echo "[1/5] 创建表空间: ${TABLESPACE_NAME}..."
psql -h "$DB_HOST" -p "$DB_PORT" -U "$ADMIN_USER" -d postgres <<EOF
-- 如果表空间目录不存在，请确保操作系统层面已创建并授权
-- 示例: sudo mkdir -p /data/postgres/tablespaces/my_ts && sudo chown postgres:postgres /data/postgres/tablespaces/my_ts
CREATE TABLESPACE IF NOT EXISTS ${TABLESPACE_NAME} LOCATION '${TABLESPACE_PATH}';
EOF

# 3. 创建数据库用户
echo "[2/5] 创建数据库用户: ${DB_USER}..."
psql -h "$DB_HOST" -p "$DB_PORT" -U "$ADMIN_USER" -d postgres <<EOF
DO \$\$
BEGIN
   IF NOT EXISTS (SELECT FROM pg_catalog.pg_roles WHERE rolname = '${DB_USER}') THEN
      CREATE ROLE ${DB_USER} LOGIN PASSWORD '${DB_PASSWORD}';
   END IF
END
\$\$;
EOF

# 4. 创建数据库并指定所有者和表空间
echo "[3/5] 创建数据库: ${DB_NAME}..."
psql -h "$DB_HOST" -p "$DB_PORT" -U "$ADMIN_USER" -d postgres <<EOF
SELECT 'CREATE DATABASE ${DB_NAME} OWNER ${DB_USER} TABLESPACE ${TABLESPACE_NAME}'
WHERE NOT EXISTS (SELECT FROM pg_database WHERE datname = '${DB_NAME}')\gexec
EOF

# 5. 在新数据库中创建 Schema 并授权
echo "[4/5] 创建 Schema: ${SCHEMA_NAME} 并授权..."
psql -h "$DB_HOST" -p "$DB_PORT" -U "$ADMIN_USER" -d "${DB_NAME}" <<EOF
CREATE SCHEMA IF NOT EXISTS ${SCHEMA_NAME} AUTHORIZATION ${DB_USER};
GRANT ALL PRIVILEGES ON DATABASE ${DB_NAME} TO ${DB_USER};
GRANT ALL ON SCHEMA ${SCHEMA_NAME} TO ${DB_USER};
EOF

# 6. 导入预先写好的 DDL 文件
echo "[5/5] 正在导入 DDL 文件: ${DDL_FILE}..."
# 使用新用户、新数据库连接，并将 DDL 导入到指定数据库中
export PGPASSWORD="${DB_PASSWORD}"
psql -h "$DB_HOST" -p "$DB_PORT" -U "$DB_USER" -d "${DB_NAME}" -f "${DDL_FILE}"
unset PGPASSWORD

echo "=========================================="
echo "恭喜！数据库初始化及 DDL 导入全部完成！"
echo "=========================================="




针对 Oracle 迁移到 PostgreSQL 过程中遇到的“无主键表”和“表被拆分”这两大经典数据校验难题，传统的基于主键比对的工具（如 Ora2Pg 自带的校验）确实无能为力。

针对这两种特殊情况，推荐使用以下成熟的解决方案和变通策略：

一、 针对“无主键表”的校验方法
当表没有主键时，无法通过 PRIMARY KEY 匹配行。核心解决思路是“全行内容哈希化（Row-level Hash）”或“引入临时行号”。

方法 1：全字段 MD5/SHA256 哈希比对（最推荐）
将每一行的所有列拼接成一个字符串，计算其哈希值（MD5），然后比对两边哈希值的集合是否一致。

Oracle 端查询示例：

SQL
-- 将各列用分隔符拼接后取 MD5
SELECT MD5(TO_CLOB(NVL(col1, 'NULL') || '|' || NVL(TO_CHAR(col2), 'NULL') || '|' || ...)) as row_hash
FROM source_table;
PostgreSQL 端查询示例：

SQL
-- 使用 row_to_json 或 string_agg 将整行转为文本并取 md5
SELECT md5(row_to_json(t)::text) as row_hash
FROM target_table t;
比对方式：将两边导出的哈希值列表导入到文件或临时表中，使用 comm、diff 或 SQL 的 EXCEPT 找出差异。

方法 2：基于临时序号（Row Number）的比对
如果表的数据量不是极大，且在导出期间表数据是静态的（无并发写入）：

在 Oracle 和 PostgreSQL 中分别通过分析函数 ROW_NUMBER() OVER (ORDER BY (SELECT NULL)) 生成一个确定性的临时行号。

将行号作为“虚拟主键”，按批次拉取进行字段逐一比对。

二、 针对“迁移后被分割的表”的校验方法
如果 Oracle 的一张大表在 PG 中被拆分成了多张表（例如按时间分区、按业务维度拆分，或分库分表），校验时需要将 PG 侧的数据“在逻辑上还原”。

方法 1：在 PostgreSQL 中创建“还原视图”（推荐）
在 PostgreSQL 中建立一个视图（View），通过 UNION ALL 或 JOIN 把被分割的表重新拼回原 Oracle 表的结构。

操作步骤：

在 PG 中创建视图：

SQL
CREATE OR REPLACE VIEW v_merged_original_table AS
SELECT * FROM table_part_2025
UNION ALL
SELECT * FROM table_part_2026;
之后，将这个视图 v_merged_original_table 直接当作一张完整的表，与 Oracle 的原表进行行数、聚合指标或上述的哈希比对。

方法 2：聚合指标分组合并校验（适合超大表）
如果数据量太大无法整体拼接，可以对比分组统计指标：

Oracle 端：按某个公共维度（如日期、状态、业务类型）统计 COUNT(*) 和关键数值列的 SUM()。

PG 端：对所有拆分表的数据进行相同的聚合统计，并将结果汇总。

比对内容：核对各个分组的 COUNT 和 SUM 是否完全一致。

三、 生产环境常用校验工具推荐
如果不想手写复杂的 SQL 脚本，可以借助以下两款专门处理复杂异构数据库校验的开源/成熟工具：

DataChecker / DataX-Cert：支持异构数据库（Oracle vs PG）的抽样对比和全量/增量对账，支持自定义无主键表的联合键或全字段校验。

Python 自研校验脚本（Pandas）：

用 Python 分页读取 Oracle 和 PG 数据。

利用 pandas.merge() 或 pd.concat() 在内存中处理拆分表的合并，并使用 df.equals() 或多列差集快速找出不一致的数据行。

从 Oracle 转向 PostgreSQL（简称 PG）时，你会发现大部分对象概念是相通的，但在底层实现和语法上有很大的不同。特别需要注意的是：PostgreSQL 原生没有类似 Oracle 的 PACKAGE（程序包）、DBLINK（直接作为对象创建）和 DIRECTORY 对象的语法，但 PG 提供了功能相同或更优雅的替代方案（如 Schema、FDW 等）。

同样为你分为 4 大类，带你看看 PostgreSQL 版本的实现：

一、 数据存储核心（Core Data Storage）
1. TABLE (表)
含义：结构化数据存储的核心单元。与 Oracle 不同的是，PG 支持更丰富的原生数据类型（如 JSONB、数组、UUID 等）。

例子：创建一个员工表，其中 emp_id 使用自增类型。

SQL
CREATE TABLE employees (
    emp_id SERIAL PRIMARY KEY, -- SERIAL 会自动创建序列并绑定
    emp_name VARCHAR(50),
    salary NUMERIC(10, 2)
);
2. SEQUENCE (序列)
含义：自动递增的数字生成器。在 PG 中，除了用 SERIAL 隐式创建外，也可以显式创建。

例子：创建一个从 1001 开始的序列。

SQL
CREATE SEQUENCE emp_seq START WITH 1001;

-- 使用时通过 nextval() 函数获取：
-- INSERT INTO employees VALUES (nextval('emp_seq'), '张三', 5000);
3. TYPE (类型)
含义：PG 的自定义类型非常强大。最常用的是复合类型（Composite Type，类似结构体）和枚举类型（ENUM）。

例子：创建一个代表周几的枚举类型。

SQL
CREATE TYPE week_day AS ENUM ('Monday', 'Tuesday', 'Wednesday', 'Thursday', 'Friday');

-- 之后可以作为表的字段类型：CREATE TABLE t (day_off week_day);
二、 逻辑视图与安全访问（Logical Views & Security）
4. VIEW (视图)
含义：虚拟表，保存一段查询 SQL。PG 的视图同样不占用物理存储空间。

例子：创建一个只看高薪员工的视图。

SQL
CREATE VIEW high_salary_emp AS
SELECT emp_id, emp_name 
FROM employees 
WHERE salary > 8000;
5. MVIEW / Materialized View (物化视图)
含义：将查询结果物理存储在磁盘上的视图。刷新时，PG 提供了 CONCURRENTLY 参数，允许在不阻塞查询的情况下进行并发刷新（需要有唯一索引）。

例子：创建并刷新一个物化视图。

SQL
CREATE MATERIALIZED VIEW dept_salary_mv AS 
SELECT emp_name, SUM(salary) AS total_sal FROM employees GROUP BY emp_name;

-- 刷新物化视图：REFRESH MATERIALIZED VIEW dept_salary_mv;
6. SYNONYM (同义词 —— PG无原生对象，用视图/Search Path替代)
含义：PostgreSQL 官方原生不支持 CREATE SYNONYM 语法。PG 通常通过配置 search_path（模式搜索路径）或者直接创建一个简单的 VIEW 来实现别名功能。

例子：用视图代替同义词。

SQL
-- 模拟 Oracle 的别名功能
CREATE VIEW emp AS SELECT * FROM employees;
7. DBLINK (远程连接 —— PG中为扩展模块或 FDW)
含义：跨库查询。在 PG 中，dblink 是一个官方自带的扩展模块，更现代、更推荐的做法是使用 FDW（外部数据包装器，Foreign Data Wrapper）。

例子：使用 PG 自带的 dblink 扩展进行跨库查询。

SQL
-- 1. 首先需要安装扩展
CREATE EXTENSION dblink;

-- 2. 直接在查询中连接远程库
SELECT * FROM dblink('host=192.168.1.100 dbname=remote_db user=res_user password=pwd',
                     'SELECT emp_id, emp_name FROM employees')
AS remote_data(emp_id INT, emp_name VARCHAR);
8. GRANT (授权)
含义：将表、视图、序列等对象的权限授予指定的用户或角色。

例子：把 employees 表的只读权限赋给用户 tom。

SQL
GRANT SELECT ON TABLE employees TO tom;
三、 存储过程与业务逻辑（PL/pgSQL Code）
9. PACKAGE (程序包 —— PG无原生对象，用 Schema 替代)
含义：PostgreSQL 没有 Oracle 的 PACKAGE 对象。在 PG 中，通常利用 Schema（模式） 来实现类似包的命名空间隔离，将相关的函数、存储过程放到同一个 Schema 下。

例子：用 Schema 模拟包的分组。

SQL
CREATE SCHEMA emp_mgmt_pkg;

-- 在该 Schema 下创建函数，调用时通过 emp_mgmt_pkg.get_monthly_sal()
CREATE FUNCTION emp_mgmt_pkg.get_monthly_sal(ann_sal NUMERIC) ...
10. FUNCTION (函数)
含义：执行特定逻辑并必须返回值。PG 的旧版本（11以前）只有函数，函数内部默认不能直接执行 COMMIT/ROLLBACK（除非用特殊方式）。

例子：创建一个计算月薪的函数（使用 PL/pgSQL 语言）。

SQL
CREATE OR REPLACE FUNCTION get_monthly_sal (ann_sal NUMERIC) 
RETURNS NUMERIC AS $$
BEGIN
    RETURN ann_sal / 12.0;
END;
$$ LANGUAGE plpgsql;
11. PROCEDURE (存储过程)
含义：PG 从 11 版本开始正式引入 PROCEDURE。与函数不同，存储过程没有返回值，并且支持在内部使用 COMMIT 和 ROLLBACK 进行事务控制。

例子：更新薪资并提交事务的存储过程。

SQL
CREATE OR REPLACE PROCEDURE update_sal (p_id INT, p_sal NUMERIC) AS $$
BEGIN
    UPDATE employees SET salary = p_sal WHERE emp_id = p_id;
    COMMIT; -- 支持事务提交
END;
$$ LANGUAGE plpgsql;

-- 调用方法：CALL update_sal(1, 6000);
12. TRIGGER (触发器)
含义：事件驱动的自动执行程序。在 PG 中，定义触发器分两步：先写一个返回类型为 TRIGGER 的触发器函数，再创建触发器本身与表绑定。

例子：

SQL
-- 1. 定义触发器函数
CREATE OR REPLACE FUNCTION log_emp_insert() RETURNS TRIGGER AS $$
BEGIN
    RAISE NOTICE '准备插入新员工: %', NEW.emp_name;
    RETURN NEW;
END;
$$ LANGUAGE plpgsql;

-- 2. 创建触发器绑定到表
CREATE TRIGGER trg_before_emp_ins
BEFORE INSERT ON employees
FOR EACH ROW EXECUTE FUNCTION log_emp_insert();
四、 物理存储与系统管理（Physical & Infrastructure）
13. TABLESPACE (表空间)
含义：定义在文件系统中的一个目录，用来指定 PG 数据库在磁盘上存储物理文件的实际位置。

例子：创建一个表空间指向服务器的某个挂载盘目录（该目录必须为空且 pg 账号有读写权限）。

SQL
CREATE TABLESPACE tbs_data LOCATION '/mnt/ssd_disk/pg_data';

-- 创建表时指定表空间：CREATE TABLE t (...) TABLESPACE tbs_data;
14. PARTITION (分区)
含义：PG 从 10 版本开始引入了声明式分区（Declarative Partitioning）。将一张大表按照某种规则，物理上拆分为多个分区子表。

例子：按范围（RANGE）创建订单分区主表和子表。

SQL
-- 创建主表（不存实际数据）
CREATE TABLE sales (
    sale_id INT,
    sale_date DATE NOT NULL,
    amount NUMERIC
) PARTITION BY RANGE (sale_date);

-- 创建真实存储数据的分区子表
CREATE TABLE sales_2025 PARTITION OF sales
    FOR VALUES FROM ('2025-01-01') TO ('2026-01-01');
15. DIRECTORY (目录 —— PG无原生对象，用系统命令/扩展替代)
含义：PostgreSQL 没有像 Oracle 那样的 CREATE DIRECTORY 对象。PG 在读写服务器本地文件时（如 COPY 命令或 adminpack 扩展），直接在 SQL 语句中指定服务器的绝对路径。

例子：在 PG 中直接利用服务器路径导出数据。

SQL
-- PG 不需要建目录对象，直接由超级用户指定绝对路径
COPY employees TO '/var/lib/postgresql/data/emp_export.csv' WITH CSV HEADER;


方案 1：使用 EXPLAIN ANALYZE 诊断死结/卡死点（第一步）
不要盲目改 SQL，先看 Postgres 到底卡在哪一步：

SQL
EXPLAIN ANALYZE 
YOUR_VIEW_SELECT_QUERY;
观察点：

看执行计划中显示的是 Seq Scan（全表扫描 1700 万行） 还是 Index Scan。

看具体是哪一个表或哪一个 Join 节点耗时最长、返回的实际行数（actual rows）和预估行数（rows）是否偏差巨大。


SQL
-- 优化思路：先把大表中能过滤出少量数据的子集通过 CTE 隔离出来，再做 Join
WITH filtered_a AS (
    SELECT id, col1 FROM a WHERE created_at > '2026-01-01' -- 尽早过滤减少数据量
)
SELECT * 
FROM filtered_a
JOIN b ON filtered_a.id = b.a_id
JOIN c ON b.id = c.b_id;
在 PostgreSQL 中，适当地使用 WITH（CTE）有时可以作为一个“优化器栅栏”（Optimizer Barrier），强制 Postgres 先执行这一步的过滤，从而避免 1700 万全表数据直接参与大循环。（注：PG 12 以后 CTE 默认可能会被内联，如果需要强制隔离，可以使用 WITH ... NOT MATERIALIZED 或根据 PG 版本调整）。
